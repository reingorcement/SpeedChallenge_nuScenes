# FlexiNet_ChassisFusion 算法问题分析与纵侧向速度估计改造方案

## 1. 当前算法存在的问题

当前 `FlexiNet_ChassisFusion` 的核心能力是估计**标量车速**，不是估计车辆二维速度。数据集在 [nuscenes_chassis.py](d:/data/Master/01_Master_1/01_Research/09_SpeedChallenge_nuScenes/FlexiNet_ChassisFusion/dataset/nuscenes_chassis.py:296) 中用相邻 ego pose 的平面位移距离除以时间得到 `speed_label`，即：

```text
speed = sqrt((x2 - x1)^2 + (y2 - y1)^2) / dt
```

这会丢失方向、正负号、纵向/侧向分量，模型只能学习“速度大小”，无法判断车辆是在前进、横向滑移、转弯侧向速度，或低速倒车等状态。

当前融合模型在 [fusion_model.py](d:/data/Master/01_Master_1/01_Research/09_SpeedChallenge_nuScenes/FlexiNet_ChassisFusion/model/fusion_model.py:75) 中采用：

```text
pred_speed = base_speed + delta_v
```

其中 `base_speed` 来自 CAN / wheel / pose 的单值速度先验，网络只学习一个标量修正量。这个设计对当前标量速度任务有效，但它天然限制了输出空间，不能直接扩展到 `v_x, v_y`。

从现有评估结果看，模型有效提升了标量车速估计：验证集 MAE 从 `base_speed` 的 `0.1995 m/s` 降到模型的 `0.0895 m/s`，RMSE 从 `0.2813 m/s` 降到 `0.1246 m/s`。但模型仍有约 `33.9%` 样本比 `base_speed` 更差，最大绝对误差约 `0.8995 m/s`，说明残差头存在过修正或场景泛化不足的问题。

当前底盘特征是单时刻 16 维向量，在 [nuscenes_chassis.py](d:/data/Master/01_Master_1/01_Research/09_SpeedChallenge_nuScenes/FlexiNet_ChassisFusion/dataset/nuscenes_chassis.py:55) 中取 `utime <= image_timestamp` 的最近 CAN 消息。问题是它没有显式建模 CAN 信号的时间序列、采样频率差异、插值、延迟或传感器时间偏移。对速度大小影响还可接受，但对侧向速度这种小量、动态量影响会更明显。

视觉输入目前是 `CAM_FRONT`、灰度、`64x64`，配置见 [default.yaml](d:/data/Master/01_Master_1/01_Research/09_SpeedChallenge_nuScenes/FlexiNet_ChassisFusion/configs/default.yaml:9)。这对标量速度估计足够轻量，但对侧向速度估计不理想，因为侧向运动、转弯、车身横摆等信息更依赖多视角、光流、道路几何和更高分辨率图像。

当前训练配置冻结视觉 backbone，见 [default.yaml](d:/data/Master/01_Master_1/01_Research/09_SpeedChallenge_nuScenes/FlexiNet_ChassisFusion/configs/default.yaml:23)。这降低训练风险，但也限制了视觉特征适配 nuScenes ego-motion 任务。现有训练仅 10 epoch，验证 MAE 仍持续下降到第 10 epoch，说明还没有明显收敛到瓶颈。

还有一个需要特别注意的问题：当前特征中包含 `pose_speed`、`accel_x`、`accel_y`、`rotation_rate_z` 等 pose 派生量，见 [nuscenes_chassis.py](d:/data/Master/01_Master_1/01_Research/09_SpeedChallenge_nuScenes/FlexiNet_ChassisFusion/dataset/nuscenes_chassis.py:104)。如果目标标签也来自 ego pose，那么这些输入可能接近标签来源。若目标是做真实车辆可部署的视觉+底盘估计，应明确区分“可部署 CAN 信号”和“nuScenes pose/定位真值信号”，避免把真值代理作为模型输入。

## 2. 算法是否有改进空间

有，而且空间主要不在简单加深 MLP，而在**标签定义、时间建模、物理先验和评估体系**。

第一优先级是做数据和基线审计。分别评估 `vehicle_speed`、`odom_speed`、`wheel_speed_mean`、`pose_speed`、当前 `base_speed`、模型输出在各速度段、转弯段、低速段、急加减速段的误差。当前整体 MAE 很低，但存在模型比基线更差的样本，说明需要定位这些样本是否集中在低速启动、制动、转弯、CAN 时间错位或特定 scene。

第二优先级是把单时刻底盘向量改成时间序列底盘特征。建议让每个视觉窗口对应一个 CAN 时间窗口，例如中心图像前后 `0.5s-1.0s` 的 wheel speed、yaw rate、steering、accel、brake、throttle 序列。用轻量 TCN、GRU 或 Transformer encoder 编码底盘序列，再与 FlexiNet 视觉时序特征融合。这样比当前单点取最近 CAN 更适合估计纵向加速度、转弯状态和侧向速度。

第三优先级是加入物理约束。车辆在正常道路驾驶中通常满足非完整约束，低侧偏时 `v_y` 接近 0，但转弯、湿滑、急操纵时可能出现可观测侧向分量。模型不应无约束预测任意 `v_y`，应把 steering、yaw rate、wheel speed、longitudinal/transversal acceleration 作为强先验，并对预测速度与 yaw rate、加速度之间加入一致性约束。

第四优先级是改进融合方式。当前是视觉特征和底盘特征拼接后 MLP 回归。建议改成“底盘先验 + 网络残差 + 置信度门控”：

```text
base_velocity = chassis_kinematic_prior
delta_velocity = network(images, chassis_sequence)
confidence = gate(images, chassis_sequence)

pred_velocity = base_velocity + confidence * delta_velocity
```

这样可以避免模型在底盘先验已经可靠时过修正，也可以在视觉或 CAN 信号不可靠时降低对应模态权重。

第五优先级是改进视觉信息。若目标包含侧向速度，应优先考虑保留 RGB、更高分辨率、多摄像头，至少加入 `CAM_FRONT_LEFT` / `CAM_FRONT_RIGHT`，更完整地观测横向运动和转弯过程。若算力有限，先把 `64x64 grayscale CAM_FRONT` 提升到 `128x128 RGB CAM_FRONT`，再考虑多摄像头。

第六优先级是重做评估。纵侧向速度不能只看速度大小 MAE，应同时报告：

```text
MAE_vx, RMSE_vx
MAE_vy, RMSE_vy
vector MAE / endpoint error
speed magnitude error
heading-aligned velocity error
turning / straight / low-speed 分组误差
模型优于底盘先验的样本比例
```

## 3. 在此基础上改造为纵侧向速度估计的方案

### 3.1 目标定义

将任务从：

```text
输入: images, chassis, base_speed
输出: speed
```

改为：

```text
输入: images, chassis_sequence, base_velocity
输出: ego-frame velocity = [v_x, v_y]
```

坐标系固定为 nuScenes ego/body frame：

```text
v_x: 车辆前向速度，单位 m/s
v_y: 车辆左向速度，单位 m/s
```

保留标量速度作为派生量：

```text
speed = sqrt(v_x^2 + v_y^2)
```

不要再把 `speed` 作为唯一监督目标。

### 3.2 标签生成方案

用 ego pose 生成二维速度标签。推荐使用中心差分而不是当前的 center-to-next 单边差分：

```text
p_prev = ego position at previous frame
p_next = ego position at next frame
dt = t_next - t_prev

v_world = (p_next - p_prev) / dt
v_ego = R_world_to_ego(center_pose) * v_world

target_velocity = [v_ego_x, v_ego_y]
```

如果当前帧没有前后帧，则丢弃该样本，不用填 0。当前实现中末端帧速度缺失时返回 0，这对标量任务影响有限，但对二维速度会引入错误监督。

训练标签可以用未来帧，因为标签是监督信号；但模型输入必须保持因果，不使用未来 CAN 信号。如果要严格在线推理，视觉窗口也应只用当前及历史帧；如果是离线估计，可以继续使用以中心帧为中心的图像窗口。

### 3.3 底盘先验设计

设置两个模式，避免实验目标混乱：

```text
fair_chassis 模式:
  输入只使用真实车辆可部署信号：
  vehicle_speed, wheel_speed, yaw_rate, steering, steering_feedback,
  longitudinal_accel, transversal_accel, throttle, brake

pose_assisted 模式:
  允许使用 nuScenes pose vel / accel / rotation_rate
  用于上限实验，不作为可部署结论
```

默认推荐 `fair_chassis`。因为如果目标标签来自 ego pose，同时输入又包含 pose velocity，那么模型可能学到的是定位真值代理，而不是视觉+底盘估计能力。

基础速度先验定义为二维向量：

```text
base_vx = vehicle_speed 或 odom_speed 或 wheel_speed_mean
base_vy = 0
base_velocity = [base_vx, base_vy]
```

更进一步可加入车辆运动学先验：

```text
yaw_rate_prior = yaw_rate
steering_prior = steering_angle
lateral_accel_prior = transversal_accel
```

但第一版不建议手工硬算复杂 `v_y`，因为 nuScenes 车辆参数、侧偏角、轮胎模型不一定可靠。第一版让模型学习 `delta_vy`，并用物理约束和分组评估控制它。

### 3.4 模型改造方案

保持 FlexiNet 视觉 backbone 和底盘 encoder 的总体结构，把回归头从 1 维输出改成 2 维输出：

```text
current:
  delta_v: [B, 1]
  pred_speed = base_speed + delta_v

target:
  delta_velocity: [B, 2]
  pred_velocity = base_velocity + delta_velocity
```

建议保留 residual 模式为主，不优先使用 direct 模式。理由是纵向速度已有强底盘先验，网络主要修正误差；侧向速度通常接近 0，也适合从 `[0]` 的 base_vy 上学习残差。

融合头建议升级为多头输出：

```text
shared_fusion_feature = fuse(visual_feature, chassis_feature)

head_vx -> delta_vx
head_vy -> delta_vy
head_uncertainty -> optional log_sigma_x, log_sigma_y
head_gate -> optional residual confidence
```

其中 `v_y` 不建议和 `v_x` 完全共享最后一层，因为二者数值分布差异很大。`v_x` 主要受轮速和纵向加速度影响，`v_y` 更依赖转向、横摆角速度、横向加速度和视觉转弯信息。

### 3.5 损失函数方案

第一版使用归一化后的 SmoothL1：

```text
L_vx = SmoothL1((pred_vx - target_vx) / sigma_vx)
L_vy = SmoothL1((pred_vy - target_vy) / sigma_vy)

L = L_vx + L_vy
```

不要直接用未归一化的 `vx, vy` 做等权损失，因为 `v_y` 通常远小于 `v_x`，会被纵向速度误差淹没。

第二版加入速度模长一致性：

```text
pred_speed = sqrt(pred_vx^2 + pred_vy^2)
target_speed = sqrt(target_vx^2 + target_vy^2)

L_speed = SmoothL1(pred_speed - target_speed)
L = L_vx + L_vy + 0.2 * L_speed
```

第三版再加入物理一致性项：

```text
d(pred_vx)/dt 与 longitudinal_accel 一致
d(pred_vy)/dt + yaw_rate * pred_vx 与 transversal_accel 近似一致
```

物理一致性项建议作为小权重正则，不要一开始强约束，否则会放大 CAN 噪声和时间同步误差。

### 3.6 训练策略

第一阶段只训练新的二维回归头和底盘 encoder，保持视觉 backbone 冻结，验证标签和指标是否正常。

第二阶段解冻 FlexiNet 的后几层，用较小学习率微调视觉特征。当前配置冻结 backbone 且第 10 epoch 仍在下降，因此二维任务不应只训练 10 epoch。建议用早停机制，以验证集 `vector RMSE` 或 `MAE_vx + MAE_vy` 作为选择 best checkpoint 的主指标。

第三阶段引入底盘序列 encoder。此阶段再比较三组模型：

```text
chassis-only velocity residual
vision-only velocity residual
vision + chassis fusion residual
```

只有 fusion 模型显著优于 chassis-only，才能证明视觉信号对纵侧向速度估计有实际贡献。

### 3.7 评估与验收标准

二维速度版本至少输出以下指标：

```text
MAE_vx_mps
RMSE_vx_mps
MAE_vy_mps
RMSE_vy_mps
vector_endpoint_error_mps
speed_magnitude_MAE_mps
base_MAE_vx_mps
base_MAE_vy_mps
gain_vs_base_vx
gain_vs_base_vy
```

必须单独评估以下场景：

```text
低速: speed < 2 m/s
中速: 2-10 m/s
高速: > 10 m/s
直行: abs(yaw_rate) 小
转弯: abs(yaw_rate) 大
强制动: brake 或 longitudinal_accel 大
明显横向运动: abs(target_vy) 高分位
```

验收标准建议分两层：

```text
基础通过:
  vx 明显优于 base_vx
  vy 不退化为恒定 0，并在转弯/横向高分位样本优于 base_vy=0

较好结果:
  fusion 模型同时优于 chassis-only 和 vision-only
  模型比 base_velocity 更好的样本比例超过 65%
  高误差样本不集中在少数 scene 或时间同步异常片段
```

## 4. 推荐实施顺序

第一步：不动模型，先重做标签和评估定义。把当前标量 `speed` 扩展为 `velocity=[vx, vy]`，同时保留 `speed` 作为派生指标。

第二步：把 `base_speed` 扩展为 `base_velocity=[base_vx, 0]`，模型输出从 1 维改成 2 维，继续使用 residual 融合。

第三步：增加 `vx/vy/vector` 指标、预测 CSV 字段和诊断图，确认二维速度结果可信。

第四步：做 chassis-only、vision-only、fusion 三个消融实验，判断视觉是否真的贡献了纵侧向速度估计。

第五步：如果二维任务验证有效，再引入底盘时间序列 encoder、多摄像头或更高分辨率视觉输入。

## 5. 明确假设

默认目标是估计 ego/body frame 下的车辆速度：

```text
x 轴为车辆前向
y 轴为车辆左向
单位为 m/s
```

默认第一版仍使用 nuScenes ego pose 生成监督标签，但不把 pose velocity / pose acceleration 作为可部署模型输入。

默认保留当前项目结构、FlexiNet backbone 和 residual fusion 思路，只把标量速度任务扩展为二维速度任务。

默认不在第一版引入复杂轮胎模型或车辆参数标定；先用数据驱动残差学习和轻量物理正则验证可行性。

默认当前代码不修改。本方案只是后续改造说明。
